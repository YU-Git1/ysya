# 压缩鸭本地压缩策略

## 当前实现

当前版本在首次访问后可作为 PWA 离线运行，图片字节始终在浏览器本地解码、编码和导出，不上传到服务器，也不调用 AI。离线启动依赖首次联网访问后由 Service Worker 缓存完成；邮箱登录仍需要网络和 Supabase 配置。

- JPG/JPEG、WebP、AVIF：每张图最多编码五个质量候选，按原文件大小和压缩档位计算目标体积，再用 128 像素长边内的样本计算包含透明度的预乘 RGBA 平均误差；在达到档位阈值的候选中选最接近目标体积的结果。该像素误差是轻量筛选指标，不是 SSIM 或感知质量认证。
- PNG：使用 OxiPNG 的 WebAssembly 无损优化，1-4 档对应优化级别 1-4，第 5 档采用级别 4；不降低像素质量。原 PNG 优化后若没有变小则保留原文件。转换成 PNG 仍会遵从用户选择的格式，结果可能大于输入。
- GIF：原格式默认逐字节保留动画。主动输出 GIF 时对所有解码帧重编码，并根据 1-5 档使用 256 到 64 色的调色板；档位越高文件通常越小，但颜色损失也会增加。
- TIFF、HEIC：默认原样保留。转成 JPG、PNG、WebP 或 AVIF 时，当前解码路径仅处理 TIFF 第一页或 HEIC 首个解码结果；多页/连拍内容不会合并进单张输出。
- 原格式 JPG、PNG、WebP、AVIF：重编码结果没有变小时保留输入字节，避免“压缩后”反而膨胀。PNG 和原样保留的 GIF、TIFF、HEIC 不使用有损压缩档位。
- 暂停：编码候选之间检查暂停状态，不阻塞页面主线程的任务控制。
- 批量：依据设备内存与逻辑核心数使用 1-2 个 worker；内存未知时按保守的 4 GB 档处理。
- ZIP：逐文件流式读取，采用 DEFLATE level 6，并在内存中汇集压缩块生成下载文件。浏览器 ZIP 下载会额外占用与导出文件体积相近的内存；超大批次优先使用文件夹导出。

## 为什么不用固定质量

同一个质量数字在不同图片上的体积和观感差异很大。纯固定质量会让简单图片浪费体积，也可能让纹理复杂的图片出现明显损失。候选编码加视觉阈值可以根据图片内容自动选择更合适的质量档位。

## 当前边界

浏览器 Canvas 的编码器不是专业的 MozJPEG、pngquant、libavif 或 GIF 优化器，因此当前实现适合作为本地 MVP 的可靠基线，不能宣称已经达到这些原生编码器的极限压缩率。EXIF、ICC、XMP 等元数据不会被完整保留，JPG 透明通道会以白色背景输出。

## 下一步的专业编码层

更高压缩率和更好的速度仍可通过专用 WebAssembly 编码器及 Web Worker 提升：

| 格式 | 推荐本地编码器 | 处理策略 |
| --- | --- | --- |
| JPG/JPEG | MozJPEG | 感知量化、渐进式 JPEG、去除无用元数据 |
| PNG | pngquant + oxipng | 颜色量化后再无损重排；有透明通道时保留 alpha |
| WebP | libwebp | 有损/无损双路径，按内容选择 |
| AVIF | libavif + libaom | 高压缩率，提供速度档位和兼容性提示 |
| GIF/APNG | gifsicle / oxipng | 调色板优化、帧差分、重复帧删除 |
| TIFF | libtiff | 保留通道和位深，默认无损压缩 |
| HEIC | libheif | 解码后明确提示输出格式，避免伪装为原格式 |

## 画质保护原则

1. 先识别颜色空间、透明通道、位深和动画属性。
2. 无损格式默认不丢像素；有损格式使用感知指标和人工可解释的质量档位。
3. 不只看 SSIM：同时检查边缘、文字、细线和透明边缘，避免平均指标掩盖局部损失。
4. 结果页显示原始大小、输出大小、节省比例、输出格式和是否保留元数据。
5. 用户可以选择“体积优先、平衡、画质优先”，而不是把算法决策完全隐藏。
6. 所有编码放进 Worker；大图分批处理，避免手机页面卡死。

## 格式支持路线

当前第一阶段包含 JPG、PNG、WebP、AVIF、GIF、TIFF、HEIC 的本地导入，JPG、PNG、WebP、AVIF 的页面格式选择，GIF 动画转换、文件夹输入、ZIP/文件夹导出及首次联网后离线使用。更专业的 MozJPEG、oxipng/pngquant、libwebp/libavif、完整 TIFF 多页和 HEIC 编码，仍属于后续编码层升级；Tauri 桌面版可复用任务模型并进一步改善文件系统和大批次内存管理。
